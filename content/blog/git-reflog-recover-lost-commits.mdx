You know the feeling. You meant to undo one commit, you typed `git reset --hard HEAD~3`, and now you're staring at a working tree with three days of work gone. Your heart drops, you open the browser to search "recover deleted commits", and the answer is always the same calm reassurance:

It's fine. Git kept a receipt. The **reflog** remembers everything.

## What the reflog actually is

The reflog ("reference log") is a local history of where your `HEAD` has pointed. Every time you commit, reset, rebase, merge, checkout, or stash, an entry is written. It's Git's own undo history, a log of the *changes to the log*.

```shell-session
git reflog
```

Output looks something like this:

```shell-session
a1b2c3d HEAD@{0}: reset: moving to HEAD~3
9f8e7d6 HEAD@{1}: commit: add payment retry logic
5a4b3c2 HEAD@{2}: commit: fix auth cookie expiry
```

`HEAD@{1}` means "where HEAD was one step ago", and that commit is still there, fully intact, waiting for you.

## The classic recovery

You did the `reset --hard`, you panicked, you stopped. Here's the fix. First, see where your work lives:

```shell-session
git reflog
```

Find the commit you want (the one right before the reset), then point your branch back at it:

```shell-session
git reset --hard HEAD@{1}
```

Or, if you'd rather be gentle, cherry-pick just that commit onto your current branch:

```shell-session
git cherry-pick 9f8e7d6
```

Either way, your work is back. The reflog is why "deleted" commits aren't really deleted.

## Recovering a deleted branch

You deleted a branch that hadn't been merged (oops). If you had that branch checked out at some point, the HEAD reflog still holds a `checkout:` entry mentioning it. `git reflog | grep feature-email` finds the tip, and `git branch feature-email <hash>` brings it back.

But the dependable path doesn't rely on the reflog at all. A deleted branch becomes *dangling commits*, reachable from nothing, but still sitting on disk. `git fsck` hunts those down:

```shell-session
git fsck --lost-found
```

That lists every dangling commit. Grep the output for your branch's last commit message, then recreate the branch from the hash:

```shell-session
git branch feature-email 7c4a9f2
```

Instant resurrection. The commits were dangling, not destroyed.

## Rebase gone sideways

Mid-rebase, you realize it's a mess and want out. `git rebase --abort` handles most cases. But what if you already *continued*, and the results are worse than the original?

```shell-session
git reflog
# find the commit that was HEAD before the rebase
git reset --hard <that-hash>
```

The pre-rebase state is in the reflog, always. Rebase doesn't delete the old commits until the reflog entries expire, which takes about 90 days by default.

## When the reflog can't save you

A few honest caveats:

- The reflog is **local**. If the work never existed on your machine (it's on a server, and the remote branch was force-pushed over), your reflog won't have it. But the remote's reflog or a colleague's clone might.
- Reflog entries **expire** (90 days by default for unreachable commits). Very old "lost" work may be genuinely gone.
- `git gc` with aggressive settings can prune dangling commits sooner.

## Conclusion

The reflog is the reason I stopped fearing destructive git commands. `reset --hard` stops being a heart attack and starts being a tool, because I know the receipt exists. Next time you panic, and you will, type `git reflog` before you type anything else.
