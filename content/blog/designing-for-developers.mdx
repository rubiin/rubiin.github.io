Developers are the most design-literate users on earth and the least forgiving. They notice a 40ms lag, a tooltip that gets in the way, a docs page that requires three clicks to find the obvious. Building Atlas Docs — an MDX documentation platform — taught me more about UX than any consumer app ever did.

This is what I learned, in the order I learned it.

## Fast is the feature

For a docs site, *speed is the interface*. Every millisecond of latency is a tax on a user who is mid-thought. Sub-100ms search, instant navigation, offline reading: these aren't nice-to-haves, they're the product.

Think about the context a developer is in when they open your docs: they are in flow, debugging, mid-refactor, one tab away from their editor. Every hop between pages is a context switch. If the docs feel slow, the developer doesn't blame the network — they blame the *tool*, and then they go back to Stack Overflow.

The performance budget for Atlas was unforgiving: navigation had to be instant (no full reloads, ever), search had to return results in under 100ms, and the whole thing had to work offline. That last one sounds like a luxury until you're on a train with a deadline. Offline reading turned "docs" from a website into a *utility* — the kind of thing you forget is even loading because it's always there.

The technical choices followed from the product goal, not the other way around: a prebuilt search index, route-level code splitting so every page ships only its own code, and a service worker that caches the entire site for offline use. None of this was exotic. All of it was *prioritized*, which is the actual skill.

## Show the code, then explain it

Developers read code first and prose only when confused. So our docs pages put the code sample above the paragraph that explains it. The typography does the rest: mono for code, generous line height for prose, and a reading width that doesn't require neck gymnastics.

This ordering seems trivial and is quietly radical. Most documentation is written like an essay: introduction, context, then — finally, after two scrolls — the actual API call. Developers don't read essays; they scan. Give them the thing they came for (the code) immediately, and the prose becomes enrichment rather than a tollbooth.

A few concrete rules we shipped:

- **The code sample is the hero of the page.** It gets the widest column, the clearest contrast, and the most space.
- **Explanations are optional reading.** If a paragraph is required to use the API correctly, it belongs in a warning callout, not buried in a paragraph.
- **One example per concept, done well.** A copy-pasteable example that works beats three theoretical ones.

The typography matters more than people give it credit for. Mono at the right size, a comfortable reading measure (about 65 characters), generous vertical rhythm, and headings that create a visible outline you can skim. A docs page should be scannable in three seconds — you should be able to land, find the answer, and leave before you've even consciously "read" anything.

## Respect the flow

The worst thing a tool can do is break the user's flow. That means: no modal that hides the code, no scroll-jacking, no animation that takes longer than the thought it interrupts. Motion should *frame* the content, not compete with it.

The anti-patterns are everywhere in developer tools. Loading spinners that appear and disappear too fast to register (or so slow they feel broken). Smooth-scroll hijacking that makes anchor links feel drunk. Hover animations that trigger on the way to clicking something else. Tooltips that cover the exact element you were about to read.

The discipline is restraint. If an interaction doesn't serve a goal — orienting the user, confirming an action, preventing an error — it should probably not exist. Developers are power users; they optimize for throughput, and anything that gets between them and their goal is friction, no matter how pretty.

## The quiet win: copy buttons everywhere

The single most-loved feature was a copy button on every code block. It saved developers from selection-miss and stray spaces. Small interactions compound into a feeling of care — and care is what makes a tool feel premium.

We shipped the copy button as an afterthought — a tiny icon in the corner of every code block, barely visible until you hover. It turned out to be the most-used feature on the site, by a wide margin. The lesson: the features that win are the ones that remove *micro-friction* from the most common workflow. Selecting code with a mouse, dragging to the end, missing the last character, pasting a truncated snippet — that whole dance happened hundreds of times a day, invisibly, until a single button deleted it.

We added a few more micro-wins with the same philosophy: click-to-copy on terminal commands, "open in editor" links next to file paths, keyboard navigation for every interactive element, and instant inline anchors on every heading so you can link to the exact section you're reading. None of these is a headline feature. Together they are the difference between a site you use and a site you *rely on*.

## Designing for the reader's future self

The best documentation isn't read once and forgotten — it's re-opened every time a skill fades. That means designing for search, for skimming, and for the person who has already forgotten they read this page before. Breadcrumbs, related links, and a table of contents aren't decoration; they're the wayfinding that lets a returning reader get back to the exact answer in one move.

The throughline of everything Atlas taught me: developer tools win on *respect*. Respect for the user's time (speed), their attention (code-first), their flow (restraint), and their muscle memory (micro-wins). Build with that respect and developers will forgive almost anything else. Ignore it, and no amount of polish will save you.
