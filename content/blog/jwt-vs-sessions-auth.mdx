Every few months a blog post declares sessions dead, or declares JWTs a security hole, and the discourse starts again. Both camps are right about the other's weaknesses and mostly wrong about their own. The real question isn't "which is better". It's "who is your API serving, and what do you need to do when a session goes bad?"

## How sessions work

The server keeps the state. On login, it creates a session record (in a database or Redis), gives the client an opaque ID in a cookie, and looks the session up on every request.

```text
login → server stores session → client gets session_id cookie
request → server looks up session_id → reads user from store
```

**The superpower: instant revocation.** Someone's account is compromised? Delete the session row (or one row per device) and they're out, immediately, everywhere. That's the feature you can't easily get with tokens.

**The cost:** every request is a database or Redis lookup, and every instance of your API needs access to the same session store. If your API spans multiple regions, the store has to span them too.

## How JWTs work

The token holds the state. On login, the server signs a token containing the user's identity and an expiry, and hands it to the client. Every request, the server verifies the signature. No storage, no lookup.

```text
login → server signs token → client stores it
request → server verifies signature → trusts the claims
```

**The superpower: statelessness.** Any instance, any region, any edge node can verify a token without touching shared state. That's why tokens dominate distributed, multi-service, and edge-rendered architectures, and why third-party integrations (OAuth flows, mobile SDKs) almost always end up token-based.

**The cost:** revocation is hard. A stolen token is valid until it expires, and "log me out everywhere" requires a blacklist, which means you're keeping server-side state anyway, just for the bad cases.

## A practical decision tree

**Default to sessions (HttpOnly cookie) when:**
- You control the frontend and backend (a classic web app).
- You need instant revocation, per-device logouts, or server-side MFA/session management.
- You're comfortable with a session store.

Use a cookie with `HttpOnly`, `Secure`, and `SameSite=Lax`. That combination blocks the scariest attack classes: XSS can't read the cookie, and cross-site scripted requests won't carry it. (Lax still allows plain top-level navigations, which is fine for a JSON API.)

**Choose short-lived JWTs when:**
- Your API is consumed by mobile apps or third parties that can't rely on browser cookie behavior.
- You're building microservices or an edge-deployed API where shared state is a real cost.
- You need authentication to cross service boundaries without a round-trip.

If you go JWT, do it properly: **short access tokens** (5-15 minutes), a **refresh token stored server-side**, and rotation. Each refresh issues a new refresh token and invalidates the old one. Long-lived access tokens with no refresh flow are where "JWT horror stories" come from.

## The mistakes both sides make

- **Storing a JWT in localStorage.** Any XSS can read it, and unlike a cookie, there's no HttpOnly to save you. Keep tokens out of JavaScript-accessible storage where you can.
- **7-to-30-day access tokens.** A leaked token with a month-long shelf life is a ticking time bomb. Short access + refresh is the pattern, not a suggestion.
- **Sessions without an expiry.** An eternal session cookie is a session that never gets revoked by time, only by incident.
- **Rolling your own.** Use a well-tested library (`jose`, `jsonwebtoken`, your framework's session middleware) and don't hand-roll signature verification.

## Conclusion

Sessions give you control; tokens give you reach. For a typical web app, start with sessions in an HttpOnly cookie. It's the safest default and revocation is free. Reach for short-lived JWTs when your architecture actually needs statelessness. And whatever you pick, the security properties come from how you store and expire things, not from which side of the argument you're on.
