When we replatformed a legacy Angular app to React, our north star wasn't a feature — it was a number: 47% faster LCP. The replatform shipped 12 minutes of release-time savings too, but the load time is what customers felt.

This post is the practical playbook: how to set budgets, where the wins actually came from, and why performance is a product decision rather than an engineering chore.

## Start with a budget

A performance budget is a contract with your future self. Ours:

| Metric | Budget |
| --- | --- |
| LCP | < 2.5s on 4G |
| Total JS | < 220 KB gzipped |
| CLS | < 0.05 |
| TBT | < 200ms |

Write it down. Enforce it in CI. The budget is the product spec.

A budget only works if it's *enforced*. We wired the bundle-size budget into CI — a GitHub Action that fails the build when the entry-point JavaScript grows past the limit with a diff of what pushed it over. That single automated check did more for performance than any number of "please be careful with imports" emails. When a performance regression arrives as a failed build instead of a complaint from users, it gets fixed in the same PR that caused it.

The four metrics above cover the four failure modes of a slow web app:

- **LCP** — how long until the main content is visible. The first impression.
- **Total JS** — the tax every user pays to run your app, even users who only see one page.
- **CLS** — how much the layout jumps while loading. Layout shift is the most underrated user-experience killer; it causes mis-clicks and a general sense of unreliability.
- **TBT** — how long the main thread is blocked. A page can paint fast and still feel dead if the thread is frozen processing JS.

## Route splitting is table stakes

With React, every route should ship only its own code. The old app shipped one 1.2 MB bundle for the login page. After splitting, the entry point was 68 KB.

Route splitting is the highest-leverage, lowest-effort performance win in a modern React app. The framework gives it to you almost for free (TanStack Router and React Router split routes automatically; Next.js and TanStack Start do it per route by default). The work is discipline: keep your *entry chunk* lean by pushing heavy libraries behind lazy boundaries.

The three big wins on our replatform:

1. **Route-level code splitting** — one chunk per route, lazy-loaded. The login page stopped shipping the charting library. Obvious in hindsight, invisible in the old architecture.
2. **No heavy libraries on the critical path** — the 3D viewer's WebGL code loads only where the 3D viewer exists. This is the same principle one level deeper: not just routes, but *features within* routes.
3. **Image optimization** — modern formats (AVIF/WebP), explicit dimensions (kills CLS), and `loading="lazy"` below the fold. Images are still the biggest bytes on most pages; most teams ship them as an afterthought.

The result: the median page went from 1.2 MB of JavaScript to 68 KB at the entry, with per-route chunks that averaged well under the budget. The 47% LCP improvement came mostly from this one architectural change plus the images.

## Measure in production, not just lab

Lab metrics (Lighthouse) tell you what *could* be fast. Field data (Core Web Vitals) tells you what your users *actually* experienced. We built a tiny RUM collector and watched the 75th percentile, not the median.

Lighthouse is a useful guardrail and a terrible scoreboard. It runs on a clean machine with a simulated network; your users are on a 2019 phone with eighteen background tabs. We kept the Lighthouse CI check (it catches gross regressions) but made product decisions from field data: Real User Monitoring reporting LCP, CLS, INP, and TBT from actual sessions.

Two things surprised us:

- The 75th percentile was consistently 2–3x the median. Optimizing for the median is optimizing for your best-case users. The p75 is where the pain lives.
- "Fast on the office network" hid a slow-tail problem: users on slower connections got the same JS weight with none of the fast network. This is why *bytes* (total JS) matter as much as *timings* — a budget on JS size is a budget that travels with the user.

## Performance is a trust signal

Users can't articulate why a site feels *right*, but they feel it. A fast site says "this is maintained, this is serious." Speed is a feature users never ask for and always notice.

There's research on this, but you don't need it: think about the last time you abandoned a site because it was slow, and the last time you felt quietly impressed that something loaded instantly. Speed is a proxy for reliability, competence, and care. A fast site doesn't just convert better — it *feels* better to be on, and that feeling compounds across every visit.

The whole framing of the replatform changed when we stopped calling it "the performance work" and started calling it "the trust feature." Budgets became product decisions. The team argued about bytes with the same seriousness as feature scope. And the customers who never read a single blog post about web performance voted with their sessions — the ones that came back.

If you take one thing from this post: pick three numbers, write them where everyone can see them, and make CI enforce them. The rest is craft. The numbers are the product.
