For a year, our Figma file and our production CSS told two different stories. The buttons were `#4F46E5` in the mockup and something sadder in the build. The fix wasn't discipline — it was a pipeline.

This is the story of how we built one, the mistakes we made along the way, and the rules that actually stuck.

## The anatomy of drift

Designers tweak a color in Figma. Engineers eyeball a hex in CSS. The next designer inherits both. Multiply by forty components and two years, and the product looks like it was designed by a committee of ghosts.

Drift is not a people problem. It's a *plumbing* problem. Designers are doing their job — iterating on the visual language. Engineers are doing theirs — encoding that language in code. The failure is that the two artifacts (Figma file, CSS) are disconnected, so every iteration in one silently forks the other. Blaming the team for drift is blaming the river for flowing downhill; the only real fix is to change the slope.

## One source of truth

We moved to a token pipeline: Figma Tokens → JSON → build-time transformation into CSS variables, Tailwind config, and SCSS. One change in the source becomes every artifact:

```json
{
  "color": {
    "primary": {
      "value": "#4F46E5",
      "type": "color"
    }
  }
}
```

The pipeline looks like this:

1. Designers edit tokens in a Figma plugin (Figma Tokens / Tokens Studio).
2. The plugin commits a `tokens.json` to the repo on every design change.
3. A build step transforms that JSON into `:root` CSS variables, Tailwind theme extensions, and any platform-specific formats.
4. CI validates the tokens — every value typed correctly, every reference resolvable, every alias pointing at an existing token — and fails the build otherwise.

The key property: there is exactly one place a color can be defined, and it is not a component file. Components can only *reference* tokens, and the linter enforces that.

## Tokens are contracts

The real win wasn't automation — it was that tokens became a *contract* between design and engineering. When a token exists, neither side improvises. Naming becomes a shared vocabulary: `color.primary`, not `blue-600` in one place and `indigo` in another.

The naming rules that matter:

- **Semantic, not literal.** A token is `color.surface`, `color.text.muted`, `space.md` — never `blue-500`, `gray-2`, `16px`. The whole point is that the *meaning* is stable while the *value* can change. When the brand shifts from indigo to violet, `color.primary` updates everywhere and nothing else needs to touch.
- **Aliases compose.** Primitives (raw values like `blue-600`) sit at the bottom. Semantic tokens (`color.primary`) point at primitives. Component tokens (`button.background`) point at semantic tokens. Changing the brand = editing a handful of primitives.
- **Rename is a breaking change.** Token names are API. We versioned them and ran a deprecation window on renames, the same way you'd deprecate a function signature.

The vocabulary was the thing that saved us. Before tokens, "that blue" meant three different hex values depending on who you asked. After tokens, "use `color.primary`" is unambiguous — and a code review can check it mechanically.

## Building the pipeline: what we'd do differently

Our first attempt was a hand-rolled script that string-replaced hex values in CSS. It worked for exactly one rename, then rotted. We rebuilt it properly: a JSON schema for tokens, a transform that outputs CSS custom properties, and a linter that rejects raw values in components.

If I were starting over, I'd reach for an established format rather than inventing one. The token landscape has consolidated around a few open standards (Style Dictionary and the W3C Design Tokens spec being the main ones), and adopting a standard means tools, plugins, and other teams can consume your tokens without a bespoke adapter.

We also learned to *never* hand-edit generated output. If a developer needed a value the tokens didn't have, the answer was "add a token," not "inline a value." The linter was the enforcement mechanism, and it caught dozens of violations a month in the early days.

## Rules that stuck

- Tokens are semantic (`surface`, `text-muted`), not literal (`blue-600`).
- No raw values in components — ever. The linter enforces it.
- Version tokens, and let design ship breaking changes through a review.
- One file is the source of truth; everything else is generated and treated as build output.

A year later, the drift is gone. Design can experiment in Figma and the changes land in code as a pull request with a clean diff. The pipeline is the least interesting part — the *vocabulary* is what saved us. If your team is fighting color drift, stop asking people to be more careful. Change the slope.
